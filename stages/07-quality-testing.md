# Этап 7. Качество кода и тестирование (постоянно)

Тесты это не про покрытие, а про скорость уверенных изменений. Команда, которая боится менять код, теряет деньги быстрее, чем команда, которая держит тесты. На этом этапе цель не выучить xUnit, а понять, какие тесты что окупают.

## Виды тестов и где какие нужны

* Unit-тесты: чистая логика, доменные правила, алгоритмы. Запускаются за миллисекунды, не трогают БД и сеть.
* Интеграционные тесты: связки нескольких компонентов, обычно с реальной инфраструктурой через Testcontainers (Postgres, Redis, RabbitMQ в Docker).
* Контрактные тесты (Pact, Verify): фиксируют контракт между сервисами, защищают от breaking changes на стороне поставщика.
* End-to-end: проверяют пользовательские сценарии целиком. Дорогие в поддержке, держим минимальный набор для smoke-проверок.
* Тестовая пирамида против тестового трофея: для backend на .NET трофей (большая доля интеграционных тестов через WebApplicationFactory) часто окупается лучше классической пирамиды.

## Инструменты

* Фреймворки: xUnit как стандарт de facto, NUnit там, где исторически прижился. MSTest почти не встречается в новых проектах.
* Ассерты: FluentAssertions (внимание к смене лицензии после версии 8, рассматривайте Shouldly или встроенный xUnit assertions). AwesomeAssertions как форк.
* Моки: NSubstitute предпочтительнее Moq из-за лицензионных скандалов 2024 года и более чистого API.
* Снапшоты: Verify для проверки сложных объектов и сериализованных payload.
* Property-based: FsCheck и CsCheck для алгоритмов и парсеров.
* Архитектурные тесты: NetArchTest и ArchUnitNET для фиксации правил вроде «домен не зависит от инфраструктуры».
* Мутационное тестирование: Stryker.NET, показывает, что тесты реально ловят, а не просто исполняют код.

## Подходы и культура

* TDD там, где требования размытые и нужен дизайн через тесты. Не догма, инструмент.
* Arrange-Act-Assert как базовый шаблон, Given-When-Then для BDD-стилистики.
* Тестируем поведение, а не реализацию. Если тест ломается на любом рефакторинге, он тестирует не то.
* Чрезмерное моканье признак плохой архитектуры. Если приходится мокать пять зависимостей в одном тесте, проблема в дизайне класса.
* Test data builders (Bogus, AutoFixture) для читаемой подготовки данных.
* Покрытие важно как сигнал, а не как KPI. 80% покрытия с тестами без ассертов хуже, чем 40% покрытия критичных путей.

## Качество кода

* Roslyn analyzers как основа: встроенные правила .NET SDK, StyleCop.Analyzers, Meziantou.Analyzer.
* EditorConfig для единого форматирования, .gitattributes для line endings.
* SonarQube или SonarCloud для трекинга качества во времени и обнаружения code smells.
* Code review культура: PR небольшие (до 400 строк), описание с контекстом, чек-лист для ревьюера. Conventional Commits для истории.
* Pre-commit хуки через Husky.NET либо lefthook: форматирование, линтинг, быстрые тесты.
* CI: прогон тестов, статический анализ, security scan (Snyk, Dependabot, GitHub Advanced Security) на каждый PR.

## Ресурсы

* «Unit Testing: Principles, Practices, and Patterns», Vladimir Khorikov, главная книга по тестам последних лет.
* «The Art of Unit Testing», Roy Osherove, третье издание на C#.
* «Working Effectively with Legacy Code», Michael Feathers, для тех, кто работает с большим существующим кодом.
* Блог Vladimir Khorikov (enterprisecraftsmanship.com), особенно серия про тестирование.
* Документация по Testcontainers (testcontainers.com) и FluentAssertions.

## Практика

1. Покрыть существующий сервис интеграционными тестами через WebApplicationFactory и Testcontainers, включая авторизацию и работу с БД.
2. Внедрить Stryker.NET, найти модули, где мутации выживают, починить тесты.
3. Написать архитектурный тест, который ломается, если домен начинает зависеть от EF Core либо ASP.NET Core.
4. Настроить CI так, чтобы билд падал при снижении покрытия критичных модулей.

## Сигналы готовности к следующему этапу

* Можете обосновать выбор между трофеем и пирамидой для конкретного сервиса.
* Поднимали Testcontainers в CI, знаете типовые ловушки (порты, очистка, параллелизм).
* Использовали мутационное тестирование и читали отчёт, а не просто запускали.
* Защищали code review культуру перед командой, которая хочет «быстрее мерджить».
